Corn-Jr

Corn-Jr is a 260M-parameter language model I trained from scratch to be a personal assistant that runs on one machine and gets things done by calling tools: web search, calls, texts, notes, date resolution. Everything was built for it: the tokenizer, the training corpus, the model, and the runtime around it. It all runs on a single RTX 3080.

The project is also a research log. Every experiment gets a numbered write-up called a finding, and there are 241 of them here. They record what I expected, what happened, and what I got wrong, including the experiments that failed. This repo holds those findings and the runtime code. The training code and weights are not included yet.

Each finding opens with a one-line headline in plain English, and the findings index lists all 241 that way. Under the headline, a finding is a working record written in the project's own vocabulary; GLOSSARY.md explains every in-house word in one sentence.

Start here

You don't need to read 241 findings. These are the ones I'd point anyone to first, grouped by what they taught me.

Models take the cheapest route the data allows

  • Finding 12 and Finding 13. The model was supposed to answer from what the search tool returned. It got 27 of 120 right. The cause was the training data: the search tool only knew 28 facts, each seen about 107 times, so the model could memorise the answers and never read the tool's output. I replaced them with about 8,700 invented facts, each seen once or twice. Same model, same token count: 120 of 120. The model did exactly what the data rewarded.
  • Finding 158. You can tell before training whether a dataset will teach an idea or a lookup table. At this scale, a wording seen more than about ten times gets answered from memory. If a cheap feature, like the first two words, settles the answer, the model learns a list and fails on anything new.

Check the measurement before believing it

  • Finding 53. Two of my own checks were grading the harness, not the model. One rejected a correct answer ("Looks like 1538 degrees Celsius.") because "looks like" wasn't on its list of allowed phrasings. The other blamed the model for answers that a token limit had cut off.
  • Finding 145. The model seemed unable to build nested structures more than one level deep. Reading every failure by hand showed it was one phrase, "two things", that it treated as plain text. With "the pair" instead, it reached depth ten on 52 to 54 of 54 chains. The structure was learned and only the wording was wrong.
  • Finding 170. My rule for calling an experiment a failure assumed run-to-run noise of 3 or 4 items out of 300. Retraining the same setup with different random seeds showed noise of up to 54, so two failures it had already called couldn't be told apart from noise. I rewrote the rule and added an automated check that enforces it.

What worked

  • Finding 112 and Finding 117. Pulling the answer out of a web page was the weakest step. A small adapter that reads each page whole raised correct answers from 389 to 513 of 721 on one seed and 388 to 510 on a second. It shipped and reads 526 of 721 in the live runtime.
  • Findings 175, 176 and 177, read in order. Teaching the model to handle "if it's raining, X, otherwise Y". In 175 it learned to write the plan correctly, if: raining -> X, on 92 to 99% of new prompts, but still followed that plan 60% of the time when it wasn't raining. In 176 the plan names both branches, and choosing the right one works for the first time. Writing the longer plan got harder, though, especially for negated conditions. 177 tested one explanation for that and ruled it out.
  • Findings 178, 179 and 180, the rest of that story. 178 found the cause: naming the second branch in the plan is what made the model blind to "not". 179 went back to the one-branch plan and, by fine-tune, it read every condition word, "not" and "unless" included, at 0.98 to 1.00. 180 kept the choice with the model and had the runtime list the options in the order the plan names them. Picking "the other one" when the condition fails was right on 864 of 864 prompts on all three starting models.

What small models showed about learning word meaning

Findings 181 to 240 are mostly experiments on 5M and 20M models, which train in hours, asking what makes a model understand words and not only predict them.

  • Finding 185. Swapping the most textbook-like web text for everyday web text raised a word-meaning test from 0.28 to 0.32 on the controls to 0.40, at little cost elsewhere. One seed, so a direction and not a settled number.
  • Finding 221. A plain table of which words appear near which, counted in one pass with no training at all, scored 51 of 96 on that test. Two 20M models trained on the same text scored 35 and 37. The information is in the data; the small model fails to pick it up.
  • Findings 236 and 237. A short test run said eight times as many small training steps would help. The full run came out worse, 3.235 against 3.041. I predicted "better" at nine in ten and was wrong, and 237 rules out the two excuses I had for it.

How the research is run

  • Predictions come first. More than half the experiments are written down before training starts: what will change, what result counts as a pass, and what counts as a failure. That way the result can't move the goalposts.
  • Findings are permanent. Numbers never change and nothing is deleted. When a later finding overturns an earlier one, the earlier one says so at the top and stays.
  • Read the raw output first. Before a number gets reported, a sample of the model's actual outputs is read by hand. Several times in this log, the measurement turned out to be wrong when the model was not.
  • Automated checks guard against silent failures. The main repo has about 110 scripts that catch the failures that never raise an error, such as a dataset that quietly mislabels 2% of its examples.

The findings refer to the model as "he". That's a habit from the project, not a claim about the model.

Running it

It was built on Python 3.11 with PyTorch and CUDA. Install PyTorch for your GPU first (the top of 0 shows how), then:

pip install -r requirements.txt
pip install "starlette>=0.37" "uvicorn>=0.29" websockets
python -m harness.studio

The studio is a local web app for chatting with the model and managing its settings. On first run it asks for a checkpoint.
